# NLQ-SQL

A natural-language-to-SQL agent over a Supabase Postgres database of
synthetic property listings. Translates a plain-English question into SQL,
validates and executes it, and self-corrects on failure. Includes a
rule-based fallback, a safety policy layer, a benchmark suite, an automatic
multi-step query planner, live update notifications, and an MCP server.

All data is synthetic, generated by `scripts/seed_supabase.py` and loaded
into a live Supabase project.

## Requirements

- Python 3.11+
- A Supabase project
- An OpenAI or Azure OpenAI API key (optional; without one, the agent
  runs on its rule-based fallback)

## Setup

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
```

Set `SUPABASE_DB_URL` in `.env`: the transaction-mode pooler connection
string from your Supabase project's Connect dialog. Optionally set
`OPENAI_API_KEY` or the Azure OpenAI equivalent to enable the LLM path.

## Usage

```bash
python scripts/seed_supabase.py      # generate and load the synthetic dataset
python demo/run_demo.py              # scripted walkthrough
python demo/run_demo.py "homes under 500000 in Denver with 3+ beds"
python scripts/eval_nlq.py           # correctness and safety benchmark
python demo/dag_demo.py              # multi-step query example (fixed steps)
python demo/auto_dag_demo.py         # multi-step query example (planned automatically, requires an LLM key)
python demo/realtime_demo.py         # live update reaction via LISTEN/NOTIFY
python -m mcp_server.server          # run as an MCP server
```

`mode` in the output is `rule-based` when no LLM key is configured, or
`llm` (`llm (self-corrected, Nx)` when a retry occurred).

## Architecture

- **Query translation** (`nlq/text_to_sql.py`): converts a question to SQL,
  validates it, and executes it against Postgres. On a SQL error, the error
  is fed back to the model and it retries, up to 3 attempts. LLM-call
  failures (rate limits, quota, network errors) are not retried the same
  way; they fall back to the rule-based path immediately.
- **LLM client** (`nlq/llm_client.py`): selects and caches the LLM provider
  (OpenAI or Azure OpenAI), independent of SQL logic.
- **Safety policy** (`nlq/policy.py`): defines the allowed tables, forbidden
  SQL keywords, and row limit. Enforced by a regex validator and a
  read-only Postgres session. Run `python -m nlq.policy` to print the
  active rules.
- **Prompt configuration** (`nlq/instructions.py`, `nlq/memory.py`):
  business rules and curated examples are stored as data, not embedded in
  code. `nlq/memory.py` also records successful queries (deduplicated) for
  few-shot retrieval, and failed queries as negative examples shown to the
  model on similar future questions.
- **Benchmark suite** (`scripts/eval_nlq.py`): checks generated SQL against
  gold queries by comparing execution results, and runs adversarial/
  injection test questions against the agent.
- **Logging**: every query logs the question, mode, attempt count, row
  count, and latency, to both the console and `data/nlq.log`. Configured
  via `nlq/logging_config.py`.
- **Multi-step queries** (`nlq/dag.py`, `nlq/planner.py`, `nlq/dag_executor.py`):
  `nlq/dag.py` runs a sequence of dependent steps, passing each step's
  result to the next, and skips downstream steps rather than running them
  on missing data if an earlier one fails. `nlq/planner.py` breaks an
  arbitrary question into that step sequence automatically (one LLM call,
  same schema/instructions the single-question path uses); `nlq/dag_executor.py`
  substitutes each step's real result into the next step's SQL as a
  parameterized value and validates every step through the same guardrail
  as any other query. `demo/dag_demo.py` is a fixed 3-step example;
  `demo/auto_dag_demo.py` is the automatic version, and requires an LLM key,
  since there's no rule-based fallback for planning itself.
- **Real-time updates** (`demo/realtime_demo.py`): listens for Postgres
  `NOTIFY` events, triggered on insert/update/delete, and re-queries when
  the data changes.
- **MCP server** (`mcp_server/server.py`): exposes the agent as a
  `query_properties` tool.

## Project structure

```
NLQ-SQL/
├── data/
│   ├── query_memory.jsonl     # recorded successful (question, sql) pairs
│   └── query_failures.jsonl   # recorded failed (question, sql, error) attempts
├── scripts/
│   ├── seed_supabase.py       # generates and loads synthetic data, installs the change-notify trigger
│   └── eval_nlq.py            # benchmark suite
├── nlq/
│   ├── text_to_sql.py         # the agent
│   ├── llm_client.py          # LLM provider selection and caching
│   ├── instructions.py        # business rules and curated examples
│   ├── memory.py              # few-shot and failure recall
│   ├── policy.py              # safety rules
│   ├── schema.py              # table definition
│   ├── logging_config.py      # shared logging setup
│   ├── dag.py                 # multi-step query runner
│   ├── planner.py             # breaks a question into steps automatically
│   └── dag_executor.py        # bridges planner output to the runner
├── mcp_server/server.py       # MCP server
└── demo/
    ├── run_demo.py             # CLI walkthrough
    ├── dag_demo.py             # multi-step query example (fixed steps)
    ├── auto_dag_demo.py        # multi-step query example (planned automatically)
    └── realtime_demo.py        # live update example
```

## Limitations

- Few-shot and failure retrieval use keyword overlap, not embeddings.
- No fine-tuned model; uses general-purpose LLMs directly.
- The planner's own decomposition isn't benchmarked, only each step's SQL
  is validated, so a plan that picks unnecessary or oddly-ordered steps
  wouldn't currently be caught.
- No multi-tool orchestration layer; the agent has a single capability.
